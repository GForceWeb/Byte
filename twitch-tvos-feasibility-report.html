1Executive Summary

The Samsung app you use is a Tizen web application — roughly 1.4 MB of JavaScript across ~24 modules — whose central engineering problem was making Twitch's modern HLS streams playable on weak TV hardware. It achieves this by running hls.js, a JavaScript HLS implementation that requires Media Source Extensions (MSE) in the browser engine.

The single most important finding of this assessment: WebKit's source explicitly disables MSE on Apple TV (ENABLE_MEDIA_SOURCE is excluded for PLATFORM(APPLETV)). hls.js therefore cannot run inside a tvOS WKWebView. Repackaging the existing app is technically possible, but only in a degraded mode that discards exactly the capability this fork exists to provide — software HLS playback of 1440p streams — while inheriting all of the Tizen-era UI and input coupling.

Meanwhile, the "hard part" of this app is trivial on Apple TV hardware: AVPlayer natively plays Twitch's usher-generated HLS playlists (including 1440p60), with full 4K-class hardware decode. A native SwiftUI client needs to rebuild only the shell — browse, chat, settings — and the web app itself becomes a reference specification rather than code to port. There are multiple working precedents, including a maintained SwiftUI tvOS Twitch client (Byte) that already supports 1440p and multistream.

Bottom line

Don't ship the web app to the Apple TV — it would be fighting the platform. A native SwiftUI/AVPlayer app reaches a better-than-parity result (native 1440p, true multistream, top-shelf integration, Siri Remote focus UI) for roughly 2–3 weeks of part-time effort to MVP. If you want a faster start, fork the GPL-licensed Byte client and customize it; both are far better uses of the Apple TV than a WKWebView shim.

2What the Samsung App Actually Is

JustTryingAI/smarttv-twitch-hls is a fork of the long-lived fgl27/smarttv-twitch (SmartTwitchTV) family — a single-page web application (HTML + vanilla JS, no framework) delivered as a Tizen widget for Samsung TVs (Tizen 2.3+), with 4,481 commits of accumulated feature work. The fork's specific purpose is to play the newer HLS-format streams (including 1440p) via hls.js where TVs' integrated players fall short.

4Option A — Repackage the Web App in a tvOS Shell

Concept: a thin SwiftUI/UIKit tvOS app hosting a WKWebView that loads the bundled app/ folder, with native bridges for remote keys and text entry.

What immediately breaks

hls.js is dead on arrival (no MSE)

The fork's defining feature — software HLS decode of 1440p streams via hls.js — cannot execute, because tvOS WebKit doesn't implement Media Source Extensions. The app's own player-selection logic (Play_HlsSupported = Hls.isSupported() && Hls.isMSESupported(), Play.js:218) would fail its capability check and drop to the native fallback path — which in this codebase means the Tizen avplay object, itself a Samsung-only API.

Salvage path: patch Play.js so the fallback uses a plain <video src="{usher m3u8 URL}">, letting Apple's native HLS stack do the work (the codebase already has URL-based quality switching for its native path, so this is a bounded edit, and it's legal under GPL since you're keeping it private).

The bridge layer you'd have to build

ConcernWork requiredRisk
Remote → app input Native focus/press handling on a hosting view; map Siri Remote presses to synthetic KeyboardEvents (the app keys off Samsung KEY_* codes; you'd remap to its internal codes) injected with evaluateJavaScript. Medium fiddly but mechanical; the app's input model is already code-based
Text entry (search, tokens) Native tvOS text field → evaluateJavaScript to set the DOM value and fire events; the Samsung system keyboard feature doesn't exist on tvOS. Medium
Playback pipeline Disable hls.js; rewrite the native-player branch to a bare <video> with the usher URL + query params; re-verify ad behavior, live-edge seeking, and reconnects through WebKit's HLS stack. Medium — this is the core of the app; every feature touches Play.js
Player capabilities WebKit's <video> exposes no quality-selection API; you switch by re-loading a different variant URL (fine), lose hls.js buffer/latency controls (real regression), and lose any hls.js-level ad logic. Medium
Persistence & updates localStorage works in WKWebView. The self-updating loader can be left pointing at GitHub Pages or frozen. Low
Rendering/perf The UI is a 2015-era DOM app with timers and large image grids; on an A12+ Apple TV it will run, but focus-driven navigation will never feel native. Low–medium

Verdict on Option A

Technically possible, genuinely working end state is degraded: you'd lose the exact capability (hls.js) the fork was created for, keep the Samsung-flavored UI, and accept input latency and maintenance drag. The only real argument for it is maximal feature parity on day one (VODs, clips, chat, follow feeds all come along) — but you'd be porting a Tizen widget to a platform where its architecture buys you nothing.

5Option B — Native tvOS Client (SwiftUI + AVPlayer)

Architecture: SwiftUI (focus-engine-native) + AVPlayer/AVPlayerViewController + Twitch GQL/usher + IRC-over-WebSocket. No third-party player library required — Twitch serves plain, undrm'd HLS that tvOS decodes in hardware.

Core playback flow (native, ~100 lines total)

// 1) Token (GQL, anonymous-capable with the public web Client-ID)
POST https://gql.twitch.tv/gql
{
  "operationName": "PlaybackAccessToken",
  "extensions": { "persistedQuery": { "version": 1, "sha256Hash": "<known hash>" } },
  "variables": { "isLive": true, "login": "channelname",
                 "isVod": false, "vodID": "", "playerType": "web",
                 "platform": "web" }
}
// → data.streamPlaybackAccessToken { value (token), signature }

// 2) Playlist
https://usher.ttvnw.net/api/channel/hls/{channel}.m3u8
  ?token={token}&sig={signature}&allow_source=true&...&platform=web&player=...

// 3) AVPlayer
let item = AVPlayerItem(url: usherURL)          // master playlist
let player = AVPlayer(playerItem: item)
player.play()                                    // 1440p60 on Apple TV 4K: hardware decode

// Quality: read item.avAsset().variantQualities? → or use
// AVMediaSelectionGroup / custom master-playlist parsing for a native quality menu.
Bonus capabilities you can't get on the Samsung app
  • Multistream: AVFoundation has no player-count limit — Byte demonstrates unlimited simultaneous streams on tvOS. The Samsung README explicitly says Tizen can't support multiple players.
  • Top Shelf content (followed-live tiles) and native player HUD polish.
  • LL-HLS: tvOS 15+ AVFoundation supports low-latency HLS natively if you opt into Twitch's lower-latency playlist behavior.
  • Reliability: WebKit/MSE/TV-keyboard quirks disappear; the only moving parts are Twitch's undocumented endpoints (same risk either way).

6Option B′ — Bootstrap from Byte (GPL-3.0)

kristianpennacchia/Byte is an unofficial Twitch (and YouTube) tvOS client built with SwiftUI, maintained as recently as June 2026, GPL-3.0, built-from-source (exactly your distribution model). It already ships:

  • Live streams + VODs, 1440p (2K) Twitch playback
  • Unlimited multistream via the ⏯ remote button
  • Follows/subscriptions listing, spoiler filtering, clickpad player options
  • OAuth sign-in flow in-app (or pre-supplied tokens via a Secrets.json)
  • Documented ad-skipping behavior when supplying a logged-in web user token
Why this matters

This is a working existence proof of Option B — and a candidate starting point. Fork it, provide your own Client-ID/Secret per its instructions, strip YouTube if unwanted, and you have a working signed tvOS Twitch client in days rather than weeks. Caveats: single-maintainer codebase (audit before you rely on it), GPL-3.0 obligations apply only if you distribute (private sideloading is fine), and its UI/UX is someone else's taste — but as a foundation or a cross-check it de-risks the native path substantially.

8Recommendation & Suggested Roadmap

Recommendation: Option B, with Option B′ as the accelerator. The web app's value was overcoming weak TV hardware and poor TV browsers — neither problem exists on Apple TV. Rebuilding the shell natively is the smaller total effort in expectation, produces a dramatically better remote-control experience, and leaves you owning a small, hackable codebase.

Phase plan (part-time pace)

PhaseDeliverableEstimate
0 · Spike Xcode tvOS project; hardcode a channel; GQL token → usher URL → AVPlayer. Confirms signing and 1440p playback on your device in the first session. 0.5–1 day
1 · MVP Channel-name entry + favorites (persisted), quality menu, full-screen playback with native HUD, basic chat overlay (read-only), device-grant sign-in. 2–3 weeks
2 · Library Followed-streams browse grid (Helix), search, game pages; live-edge auto-refresh; reconnect/backoff logic (the Samsung app's hard-won error handling is your reference spec). +1–2 weeks
3 · Depth VODs (+ VOD chat replay), clips, chat send, settings surface, optional multistream (trivial with AVFoundation), optional top shelf. +2–4 weeks
4 · Optional Ad handling via AVAssetResourceLoaderDelegate playlist filtering; BTTV/7TV emotes; low-latency mode. As desired

Signing notes for your setup

  • Free account: works, but apps expire in 7 days and need re-signing (Xcode cable-free network install); 10 App IDs/week cap. Fine for evaluation.
  • Paid program ($99/yr): development-signed installs last ~1 year, no store review, no distribution obligations — the correct choice for a permanent personal app.
  • No App Store constraints apply: no review, no special entitlements, `tv.twitch`-style bundle naming irrelevant — pick any bundle ID.

9Risks, Gotchas & Legal Notes

RiskSeverityMitigation
Twitch's undocumented endpoints (GQL PlaybackAccessToken, usher) change without notice Medium — identical for both options This is the shared, unavoidable risk of any third-party client (the Samsung app survives it via constant community patches). Keep token acquisition isolated in one module; pin the request shape; watch Streamlink's twitch plugin as the canary.
Client-ID strategy: public web ID (kimne78kx…) vs your own registration Low Register your own app at dev.twitch.tv (free). The web Client-ID works for anonymous playback tokens but is not contractually yours; a registered ID gives you your own auth identity (and Device Grant support).
Twitch ToS: unofficial clients Low in practice An unmodified, private, non-distributed viewer client is the lowest-risk configuration possible; there is no app store, no distribution, no monetization. Avoid distributing binaries or the embedded-secret pattern the Samsung app uses.
Ads: stitched ads interrupt AVPlayer playback by design Medium (quality-of-life) v1: accept them. Later: playlist-level filtering via AVAssetResourceLoaderDelegate (custom URL scheme → intercept master/variant playlists → drop ad DATERANGE segments), the same approach Streamlink uses. Note this is a cat-and-mouse with Twitch, not a one-time fix.
Device-grant login friction vs token pasting Low Implement both: device grant (primary, no TV typing) and manual token paste (fallback), mirroring the Samsung app's AddCode concept but without shipping a client secret.
VOD muted-segment gaps & clip quirks Low Known Twitch platform behavior (muted VOD segments, clip playlist shapes); the Samsung app's PlayVod/PlayClip modules document the workarounds — port the logic, not the code.
GPL-3.0 obligations Low Private personal use triggers no distribution duties. If you ever share your fork (or build on Byte), keep it GPL-3.0. Reading Play.js to port ideas is fine; copying code into a non-GPL project isn't.
Signing/expiration surprises Low Paid developer program removes the 7-day churn; otherwise calendar a weekly re-sign.
